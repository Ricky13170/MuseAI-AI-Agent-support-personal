Product vision & scope

MusicMind is a personal web music application with two entry points: direct track search and conversation with an AI Agent. The Agent helps listeners search in natural language, recommends verified catalog tracks based on stated preferences, explains its suggestions, and creates or edits playlists with user confirmation. Metadata and playback must come from authorized providers; the Agent must neither invent tracks nor extract audio without permission.

Must = MVP Should = Phase 2 Could = optional R&D

Single-Agent boundary: one Agent orchestrates tools. The music player, catalog adapter, ranking, and database operations are tools or components, not separate Agents. Persistent playlist changes require user confirmation.

Provider boundary: use metadata and playback only as authorized by each provider; do not download or extract audio or bypass protected content.

1. Functional Features & User Stories

Expand or collapse each feature below. Stable IDs support issue tracking and test-case mapping.

FEATURE-001 · 3 stories

Music Discovery & Catalog

Find music through a search bar, retrieve catalog metadata, and present playable search results.

Business value: Provides useful music discovery independently of the Agent and trustworthy records that Agent tools can reference.

In Scope
  • Search by track title, artist, and keywords
  • Display track metadata and playback availability
  • Normalize provider track IDs and distinguish recording versions
Out of Scope
  • Unauthorized downloading or storage of audio files
  • Crawling an entire music catalog
USER STORY · US-001

Search tracks by text

Must

As a listener, I want to search for songs by title, artist, or keyword so that I can choose music without talking to the Agent.

ACCEPTANCE CRITERIA
AC1 — Given a non-empty search query, when I press Search, then the system returns results with title, artist, thumbnail, duration (when available), and provider.
AC2 — Given an empty or whitespace-only query, when search is submitted, then the system does not call the provider and prompts for a query.
AC3 — Given no matching results or a provider timeout, when the request completes, then the interface shows the appropriate state and does not fabricate tracks.
USER STORY · US-002

View track metadata & availability

Must

As a listener, I want to inspect track details and playback availability before adding a track to a queue or playlist.

ACCEPTANCE CRITERIA
AC1 — Given a search result, when I open its details, then at minimum its title, artist, source ID, and original-source link are displayed.
AC2 — Given a track that cannot be embedded or played, when I select Play, then the app explains the limitation and offers a provider link when available.
AC3 — Given multiple recordings or videos with the same song title, when results appear, then the UI distinguishes their IDs, sources, or versions rather than incorrectly merging them.
USER STORY · US-003

Refine and filter music search

Should

As a listener, I want to filter results by artist or version to find the recording I want more quickly.

ACCEPTANCE CRITERIA
AC1 — Given search results, when I filter by artist or duration, then the system applies the filter using available metadata.
AC2 — Given insufficient metadata, when I apply a filter, then the result is not presented as perfectly accurate.
AC3 — Given an active search filter, when I clear it, then the unfiltered search results are restored.
FEATURE-002 · 3 stories

Player & Queue

Allow users to play content through supported provider players and manage a queue in the web application.

Business value: Delivers a real listening experience while keeping playback separate from Agent reasoning.

In Scope
  • Compliant embedded player
  • Play, pause, next, and previous within provider capabilities
  • Queue and current-track state
Out of Scope
  • Audio-stream extraction, MP3 downloads, or offline playback
  • Hiding the required player or bypassing playback restrictions
USER STORY · US-004

Play a selected track

Must

As a listener, I want to play a selected track using a supported player directly in the application.

ACCEPTANCE CRITERIA
AC1 — Given a valid provider playback reference, when I select Play, then the app loads the supported player and displays Now Playing.
AC2 — Given an embedding or playback error, when playback fails, then the app displays an error rather than claiming playback succeeded.
AC3 — Given a newly selected track, when the player confirms it is ready, then Now Playing reflects the actual player state.
USER STORY · US-005

Manage current playback queue

Must

As a listener, I want to add, remove, and reorder queue items so that I control what plays next.

ACCEPTANCE CRITERIA
AC1 — Given a valid track, when I select Add to Queue, then it appears in the correct queue position.
AC2 — Given a queue with multiple tracks, when I reorder or remove an item, then the queue changes without modifying saved playlists.
AC3 — Given an unavailable track in the queue, when its turn arrives, then the app reports the problem and allows skipping; it does not silently substitute an unverified source.
USER STORY · US-006

Handle player availability and end states

Should

As a listener, I want queue state to reflect track endings and player errors accurately.

ACCEPTANCE CRITERIA
AC1 — Given a player ended event, when a track finishes, then the queue is updated and the next track is offered according to the current state.
AC2 — Given autoplay restrictions, when the app attempts automatic playback, then it requests a user gesture if required.
AC3 — Given a player that is not ready, when the Agent requests playback, then the action is not marked successful until the player confirms it.
FEATURE-003 · 3 stories

Music Preferences & Listening Signals

Store explicitly provided listening preferences and user-approved interaction signals.

Business value: Enables controllable personalization without inventing preferences or inferring sensitive traits.

In Scope
  • Manual artist, genre, and mood preferences
  • Likes, dislikes, and minimal listening history
  • Controls for remembering and deleting user data
Out of Scope
  • Unnecessary collection of sensitive data
  • Inferring mental health or other sensitive characteristics
USER STORY · US-007

Set initial listening preferences

Must

As a new listener, I want to choose favorite artists, genres, and moods so that the Agent can personalize its first suggestions.

ACCEPTANCE CRITERIA
AC1 — Given a listener without a preference profile, when Preferences opens, then onboarding can be completed or skipped.
AC2 — Given at least one selected preference, when it is saved, then subsequent recommendation requests use that preference.
AC3 — Given no preferences or history, when recommendations are requested, then the Agent asks for criteria or provides clearly labeled general suggestions rather than claiming to know my tastes.
USER STORY · US-008

Like, dislike and favorite tracks

Must

As a listener, I want to like or dislike music so that recommendations can adapt and my favorites can be saved.

ACCEPTANCE CRITERIA
AC1 — Given a valid track, when I like or dislike it, then the feedback is stored against the correct track ID.
AC2 — Given a disliked track, when recommendations are generated, then that track is excluded by default unless I explicitly request it.
AC3 — Given existing feedback, when I change my rating, then the new feedback replaces the old without contradictory entries.
USER STORY · US-009

Listening history and privacy controls

Should

As a listener, I want to view, disable, and delete listening history to control my personal data.

ACCEPTANCE CRITERIA
AC1 — Given enabled history recording, when the player confirms a qualifying listen according to a configurable threshold, then a listening event is stored.
AC2 — Given disabled history recording, when a subsequent track plays, then no new listening event is stored.
AC3 — Given a confirmed history deletion request, when deletion finishes, then the relevant account/session history is removed and cannot be retrieved by the Agent.
FEATURE-004 · 4 stories

Single-Agent Conversational Orchestration

Understand Vietnamese and English requests, use tools, and maintain conversation state within a session.

Business value: Core Agentic AI engineering: intent routing, plan–act–observe, tool selection, and error recovery.

In Scope
  • One LangGraph Agent with a tool registry
  • Intent detection: search, recommend, playlist, playback, and Q&A
  • Clarification, action confirmation, and session state
Out of Scope
  • Multi-Agent orchestration in the MVP
  • Actions outside the allowed tool set
USER STORY · US-010

Understand intent and route tools

Must

As a listener, I want to chat in natural language so that the Agent can understand music search, recommendation, and playlist requests.

ACCEPTANCE CRITERIA
AC1 — Given a clear request such as 'find songs by artist X', when the Agent acts, then it calls the search tool rather than inventing a list.
AC2 — Given 'add the track we just found to my Study playlist', when the Agent acts, then it references the correct track and playlist from session context.
AC3 — Given an unsupported request, when the Agent responds, then it states its limitations and does not pretend an action was completed.
USER STORY · US-011

Agent tool loop with grounded results

Must

As a listener, I want the Agent to use actual music catalog results so that its actions and answers can be verified.

ACCEPTANCE CRITERIA
AC1 — Given a request requiring provider data, when the Agent responds with specific tracks, then it must first obtain them through a tool result.
AC2 — Given a tool error, timeout, or empty result, when the Agent observes it, then it may retry using a bounded alternative strategy or ask for clarification; it must not fabricate track IDs.
AC3 — Given an Agent action, when the Agent responds, then it distinguishes completed actions, proposed actions, and unavailable actions.
USER STORY · US-012

Clarify ambiguous requests

Must

As a listener, I want clarification when requests are ambiguous, rather than having the Agent act on the wrong track or playlist.

ACCEPTANCE CRITERIA
AC1 — Given multiple tracks with the same title by different artists, when 'play this one' is ambiguous, then the Agent presents options for confirmation.
AC2 — Given an unknown destination playlist, when a track-addition request arrives, then the Agent asks which playlist to use.
AC3 — Given a response to a clarification question, when the Agent continues, then it reuses the existing task state instead of restarting the whole task.
USER STORY · US-013

Manage agent context, budgets and safety

Should

As a user, I want the Agent to respond reliably, avoid infinite loops, and refrain from unintended actions.

ACCEPTANCE CRITERIA
AC1 — Given a task, when the configured step or tool-call budget is exceeded, then the Agent stops safely and explains its current state.
AC2 — Given search metadata containing forged instructions, when it enters the Agent context, then it is treated as untrusted data rather than system instructions or tool authorization.
AC3 — Given a new session, when I start chatting, then prior session state is not leaked without permission.
FEATURE-005 · 3 stories

Personalized AI Recommendations

Recommend catalog-verified tracks from natural-language preferences and explain the recommendations.

Business value: AI research focus: candidate retrieval, preference-aware ranking, diversity, and recommendation evaluation.

In Scope
  • Recommendations by mood, activity, genre, and artist
  • Remove disliked tracks and duplicates
  • Short explanations grounded in available metadata
Out of Scope
  • Analysis of copyrighted audio without authorization
  • Claiming to infer the user’s actual emotional state
USER STORY · US-014

Recommend music from natural-language goals

Must

As a listener, I want to say 'recommend calm music for studying' and receive an appropriate track list.

ACCEPTANCE CRITERIA
AC1 — Given a request containing mood, activity, or constraints, when the Agent processes it, then it generates candidate searches and retrieves tracks from the catalog.
AC2 — Given a provider without verified mood or tempo metadata, when explanations are generated, then the Agent does not assert specific musical properties such as BPM without evidence.
AC3 — Given recommendations, when they are displayed, then each track has a provider ID, title, artist, and Play/Add action.
USER STORY · US-015

Rank recommendations using preferences

Must

As a listener, I want suggestions that consider my stated preferences and feedback history.

ACCEPTANCE CRITERIA
AC1 — Given a profile with likes and dislikes, when tracks are ranked, then the scoring pipeline uses those signals and records its rationale in a trace.
AC2 — Given an identical candidate set and deterministic ranking fixture, when ranking is tested, then ordering remains stable within the configured tolerance or controlled random seed.
AC3 — Given duplicate provider video IDs in search results, when a top-N list is built, then it contains no duplicates.
USER STORY · US-016

Explain and refine recommendations

Should

As a listener, I want explanations for recommendations and the ability to refine the criteria.

ACCEPTANCE CRITERIA
AC1 — Given a recommended track, when I ask 'why this one?', then the Agent grounds its answer in my request, explicit preferences, or available provider metadata.
AC2 — Given feedback such as 'less sad music', when the Agent revises the request, then it adjusts constraints and returns a new list.
AC3 — Given no candidates satisfying all constraints, when retrieval fails, then the Agent identifies unmet constraints and suggests reasonable relaxations.
FEATURE-006 · 4 stories

Playlist Library & Agentic Playlist Editing

Let listeners manage playlists manually or ask the Agent to create and edit them through chat.

Business value: Provides observable, testable tool actions rather than chat-only recommendations.

In Scope
  • In-app playlist create, read, update, and delete operations
  • Chat-generated playlists by theme or mood
  • Preview and confirmation before bulk edits
Out of Scope
  • Writing to third-party accounts without OAuth and necessary scopes
  • Unconfirmed automatic playlist changes
USER STORY · US-017

Create and edit playlists manually

Must

As a listener, I want to create, rename, delete, and edit playlists through a standard interface.

ACCEPTANCE CRITERIA
AC1 — Given a valid playlist name, when I select Create, then one playlist with a unique ID is stored in the application.
AC2 — Given an existing playlist, when I add, remove, or reorder tracks, then the changes persist when the playlist is reopened.
AC3 — Given a playlist with tracks, when I request deletion, then the app asks for confirmation and does not remove those tracks from the music catalog.
USER STORY · US-018

Generate playlist with Agent

Must

As a listener, I want to say 'make a playlist of 10 Vietnamese indie songs for evening study' and receive a usable playlist.

ACCEPTANCE CRITERIA
AC1 — Given a topic and desired track count, when the Agent acts, then it retrieves candidate tracks and creates a previewable playlist draft.
AC2 — Given fewer eligible tracks than requested, when retrieval finishes, then the Agent reports the actual count rather than inventing tracks.
AC3 — Given user approval of the draft, when the creation tool succeeds, then the playlist is saved exactly once and the response includes its ID.
USER STORY · US-019

Modify playlists through chat

Should

As a listener, I want to ask 'remove duplicates, add five similar songs, and put slower songs first' to modify a playlist through chat.

ACCEPTANCE CRITERIA
AC1 — Given a specific playlist, when the Agent prepares edits, then it shows a diff of additions, removals, and reorderings.
AC2 — Given a rejected diff, when the request ends, then the playlist remains unchanged.
AC3 — Given an approved diff, when changes are committed, then only authorized edits apply and the changes can be inspected in history.
USER STORY · US-020

Find and organize favorite playlists

Should

As a listener, I want to browse saved playlists and quickly open my favorites.

ACCEPTANCE CRITERIA
AC1 — Given stored playlists, when Library opens, then names, track counts, and last-update times are displayed.
AC2 — Given a playlist search term, when Library is filtered, then only matching playlists for the current user/session are returned.
AC3 — Given an empty library, when it opens, then an empty state offers Create or Ask Agent.
FEATURE-007 · 3 stories

Agent Evaluation & Observability

Measure Agent task outcomes, recommendation quality, tool correctness, and failure recovery.

Business value: Makes the portfolio project demonstrably measurable rather than a subjective demo.

In Scope
  • Ground-truth evaluation dataset
  • LLM traces and tool execution timeline
  • Baseline comparisons and regression tests
Out of Scope
  • Claiming quality improvements without benchmarks
  • Treating an LLM judge as the only ground truth
USER STORY · US-021

Build reproducible Agent evaluation dataset

Must

As an AI Engineer, I want a labeled dataset of expected Agent behavior to test functionality and prevent regressions.

ACCEPTANCE CRITERIA
AC1 — Given at least 50 curated or synthetic scenarios, when evaluation runs, then each case specifies intent, constraints, expected tools/actions, and success criteria.
AC2 — Given ambiguous requests or provider failures, when cases are evaluated, then asking for clarification or failing safely may count as correct behavior.
AC3 — Given repeatable fixture, model, and configuration versions, when a report is generated, then their versions and random seeds (where applicable) are recorded for comparison.
USER STORY · US-022

Trace agent decisions and tool calls

Must

As an AI Engineer, I want to inspect Agent decisions and tool observations to debug failed or unexpected behavior.

ACCEPTANCE CRITERIA
AC1 — Given an Agent run, when it succeeds or fails, then the trace captures run ID, tool names, status, latency, and model usage if available.
AC2 — Given a tool failure, when its trace is inspected, then the error appears with secrets redacted.
AC3 — Given a user who has not agreed to storing chat text, when tracing is active, then sensitive text can be excluded or masked.
USER STORY · US-023

Compare baseline against Agent system

Should

As an AI Engineer, I want to compare an Agent with simpler search or LLM baselines and identify tasks where it adds value.

ACCEPTANCE CRITERIA
AC1 — Given a common evaluation dataset, when baseline and Agent configurations run, then task success, tool accuracy, latency, and cost are compared.
AC2 — Given a playlist-editing scenario, when results are scored, then the final playlist state is checked instead of relying only on response wording.
AC3 — Given outcomes worse than baseline, when a report is generated, then it includes failure cases and does not claim the Agent performs better.
FEATURE-008 · 3 stories

Provider Integration, Reliability & Privacy

Isolate music catalog and playback providers, control source failures, and protect personal information.

Business value: Reduces lock-in and the risks of unofficial endpoints while improving product reliability.

In Scope
  • Interchangeable provider adapter interface
  • Rate limits, retries, and error classification
  • Privacy and deletion for user data
Out of Scope
  • Bypassing DRM, geo-restrictions, or advertising
  • Unauthorized stream ripping or audio caching
USER STORY · US-024

Use an interchangeable music provider adapter

Must

As a developer, I want to switch music catalog providers without modifying LangGraph or playlist logic.

ACCEPTANCE CRITERIA
AC1 — Given a provider adapter, when search or get_track runs, then it returns a normalized object with track ID, provider, title, artists, and playback reference or availability.
AC2 — Given an unavailable provider, when search is attempted, then it produces a normalized error instead of fabricated metadata or audio from an unapproved source.
AC3 — Given an experimental InnerTube adapter, when the environment prohibits its use or the provider changes, then a feature flag can disable it; it is not the production default.
USER STORY · US-025

Handle API quota, timeout and retries

Should

As a listener, I want temporary provider failures to be explained and recoverable without losing my actions.

ACCEPTANCE CRITERIA
AC1 — Given a rate-limit or quota error, when it occurs, then the app shows a suitable message and uses bounded backoff for retries.
AC2 — Given a playlist-creation retry after a timeout, when a request is repeated, then an idempotency key prevents duplicate playlists.
AC3 — Given a source without supported playback, when I search for alternatives, then chat and playlists can still use legitimately available metadata.
USER STORY · US-026

Control personal data and external actions

Must

As a listener, I want control over my preferences, history, and actions the Agent performs on my behalf.

ACCEPTANCE CRITERIA
AC1 — Given an Agent-proposed bulk edit or destructive playlist change, when execution is requested, then explicit user confirmation is required.
AC2 — Given a personal-data deletion request, when processed, then the relevant preferences, feedback, history, and chat state are deleted from the system.
AC3 — Given a provider requiring OAuth, when it is connected, then only authorized official flows are used; the app does not store provider account passwords.

2. Non-functional Requirements

The priority levels and quality targets are proposed and must be validated in the target demo environment.

ID Area Requirement Priority
NFR-001 Performance Proposed test targets: cached local search p95 <= 2 seconds and simple Agent tasks p95 <= 12 seconds using stable fixtures/providers; report provider latency separately. Should
NFR-002 Agent Reliability Limit each run to <= 8 tool calls and a configurable timeout (suggested: 30 seconds for simple tasks); return a safe failure response rather than looping indefinitely. Must
NFR-003 Accuracy & Grounding 100% of actionable track recommendations must include valid catalog/provider track IDs observed in tool responses during the request; do not invent playback availability. Must
NFR-004 Playlist Action Safety Chat-based bulk additions, deletions, and reorderings must show a preview and confirmation before committing; verify idempotent commits. Must
NFR-005 Provider Compliance Use only provider-authorized playback methods; do not download/cache audio, bypass advertising/DRM/geographic restrictions, hide required embeds, or fake unauthorized background playback. Must
NFR-006 Security Keep API keys in server-side environment variables or a secret store; validate tool arguments; enforce tool allowlists and resist prompt injections in chat and metadata. Must
NFR-007 Privacy Minimize stored history/chat; support deletion; do not infer sensitive personal attributes from listening history; redact sensitive log data. Must
NFR-008 Testability Use Pytest unit/integration tests with mock music providers; run offline evaluations independently of live APIs and record dataset, prompt, and model versions. Must
NFR-009 Observability Record run IDs, detected intents, tools, outcomes, latency, and token usage where available; do not expose secrets in traces. Should
NFR-010 Usability Search bar and chat must be independent entry points; clearly distinguish suggestions/drafts from completed actions and provide empty, loading, and error states. Must
NFR-011 Portability The demo must run with a local database and mock provider without copyrighted audio, with optional configuration for permitted live providers. Should
NFR-012 Accessibility Support keyboard interaction for search, queue, playlists, and chat, including labeled controls and accessible player-status text. Should

4. AI Evaluation Strategy

Evaluation dataset

At least 50 labeled tasks covering search, recommendation, playlist creation/editing, ambiguous requests, provider errors, and multi-turn context. Use a mock provider for reproducible testing.

Metric What to verify
Intent routing accuracy Whether the Agent chooses the correct intent/action category.
Tool selection / argument accuracy Whether the correct tool and arguments are selected, separating Agent errors from provider failures.
Task success rate Verify final playlist and queue states and valid catalog-backed recommendations.
Recommendation quality Recall/Precision@K when relevance labels exist; acceptance/save rates, diversity, and duplicate rates.
Grounded track rate Each recommended track has a verified ID returned by the catalog.
Clarification correctness Ambiguous requests trigger clarification rather than incorrect playlist changes.
Safety / approval rate No destructive or bulk playlist action is committed without confirmation.
Latency & token cost P50/P95 latency and token usage per task, compared against baselines.

Baselines: (A) keyword search + fixed filters; (B) LLM query rewriting + search; (C) LangGraph Agent with tools, state and feedback. Do not claim that C is superior without measured evidence.

5. Open Questions, Assumptions & Risks

ID Topic Question Recommendation
Q1 Music provider Official YouTube Data + IFrame Player, another licensed catalog, or an experimental InnerTube adapter? Block public-release decisions until permitted usage is confirmed; use an approved adapter for the MVP.
Q2 Data storage Guest browser/local session or user accounts? Use a guest local profile in the MVP; add authentication later.
Q3 Playlist scope Store playlists inside the app or synchronize with provider accounts? Store locally first; external synchronization requires suitable OAuth/scopes.
Q4 Recommendation signals Stated preferences, listening history, metadata, or embeddings? Start with explicit preferences, feedback, and metadata; evaluate embeddings later.
Q5 Languages Should chat prioritize Vietnamese, English, or both? Support Vietnamese and English inputs; evaluate Vietnamese independently.
Q6 AI success criteria Prioritize tool correctness or recommendation quality? Measure both, with separate benchmarks for playlist actions and recommendations.
Music provider compliance: An InnerTube adapter may be explored in a feature-flagged research environment, but the public demo should not depend on it. Search and playback must use authorized sources/APIs. Provider content is external data, not system instructions.

6. Delivery Phases (Proposed)

Phase Title Exit criteria
Phase 0 Feasibility & Scope Verify permitted search and playback providers; prepare mock catalog; assess relevant YouTube APIs; finalize MVP and evaluation scenarios.
Phase 1 Music Fundamentals F001 search, metadata, playback, and queue; basic playlist CRUD; fixture provider.
Phase 2 Agent Core LangGraph intent routing; search and playlist tools; clarification, preview/confirmation, and session state.
Phase 3 Personalization Preference profile, likes/dislikes, recommendation ranking, explanation, cold-start handling.
Phase 4 Evaluation & Portfolio At least 50 curated tasks; baseline versus Agent; tool accuracy, traces, README, and demo video.
Phase 5 Optional Extensions Semantic retrieval and reranking, MCP adapters, advanced memory, and authorized OAuth playlist imports.
